# 자동차 부품 기술자료 검증 체크리스트 사용 설명서

## 목적

이 파일 묶음은 `자동차 도어 시스템 기술 및 신뢰성 평가 자료.xlsx`에 정리된 후보 300건을 여러 작업자가 나눠 검증하기 위한 로컬 HTML 도구입니다.

검증자는 원문을 열어 다음을 한 번에 확인합니다.

- 한국어 본문 여부
- 대상 부품 관련성
- 기술주제 적합성
- 무료 원문 접근 가능 여부
- 제목·기관·URL·발행일 등 출처 확인
- 중복 여부
- 최종 통과 / 보류 / 탈락 판정
- 청킹 단계로 넘길 메타데이터 보완

## 실행 방법

1. `index.html` 파일을 브라우저로 엽니다.
2. 작업자 이름을 입력합니다.
3. 시작 행과 검증 행 수를 입력합니다.
4. `범위 적용`을 누릅니다.
5. 각 자료를 확인한 뒤 `통과`, `보류`, `탈락` 중 하나를 누릅니다.

## Git으로 공유하는 방법

이 폴더는 정적 HTML 도구이므로 서버 설치 없이 Git 저장소로 올려서 공유할 수 있습니다.

권장 흐름:

```text
GitHub 또는 GitLab에 저장소 생성
  ↓
이 review-checklist 폴더를 저장소에 push
  ↓
작업자는 저장소를 clone 또는 ZIP 다운로드
  ↓
index.html을 브라우저로 열어 검증 작업
```

다른 작업자가 받을 때는 아래처럼 클론하면 됩니다.

```bash
git clone <저장소_URL>
cd review-checklist
```

그 다음 `index.html`을 브라우저로 열면 됩니다.

주의할 점:

- `index.html`만 단독으로 보내지 말고 폴더 전체를 공유해야 합니다.
- `app.js`, `styles.css`, `candidates.js`가 같은 폴더에 있어야 화면이 정상 작동합니다.
- 작업 결과인 `review_state.json`, `review_results.csv`, `documents.csv`는 각 작업자가 브라우저에서 내려받는 파일입니다.
- 여러 사람이 동시에 작업할 경우 각자 결과 파일을 저장한 뒤, 마지막에 합치는 절차가 필요합니다.

## 원문 파일 다운로드

검증자는 화면에서 원문을 직접 열고 내려받을 수 있습니다.

각 후보 화면에는 아래 기능이 있습니다.

|기능|역할|
|---|---|
|`원문 열기`|원문 상세 페이지 또는 PDF를 새 탭으로 엽니다.|
|`원문 다운로드`|브라우저의 기본 다운로드 동작으로 원문 URL을 저장합니다.|
|`권장 저장 경로`|해당 문서를 어느 폴더와 파일명으로 저장하면 좋은지 보여줍니다.|
|`저장 경로 복사`|권장 저장 경로를 클립보드에 복사합니다.|
|`다운로드 완료로 표시`|원문을 직접 저장한 뒤 `download_status = 다운로드완료`, `file_path = 권장 저장 경로`로 기록합니다.|

직접 다운로드 권장 흐름:

1. `원문 열기` 또는 `원문 다운로드`를 누릅니다.
2. 브라우저에서 파일을 저장합니다.
3. 가능하면 화면의 `권장 저장 경로`와 같은 위치·파일명으로 저장합니다.
4. 저장 후 `다운로드 완료로 표시`를 누릅니다.
5. 필요하면 `원문 파일 경로`를 실제 저장 위치에 맞게 수정합니다.

저장 경로 예시:

```text
downloads/PHA/PHA-0012.pdf
downloads/상신브레이크/SANGSIN-0007.html
downloads/SL/SL-0045.pdf
```

이렇게 기록해두면 `documents.csv`를 저장할 때 `file_path`와 `download_status`가 함께 나갑니다. 나중에 청킹할 때는 URL을 다시 열지 않고 `file_path`의 로컬 원문 파일을 우선 사용할 수 있습니다.

브라우저 또는 사이트 정책 때문에 직접 다운로드가 잘 안 되는 자료는 새 탭에서 열어 수동 저장한 뒤, `원문 파일 경로`에 저장 위치를 직접 입력하면 됩니다.

### 일괄 다운로드 보조 스크립트

직접 다운로드가 원칙이지만, 최종 통과 자료의 URL을 한 번에 시도해보고 싶을 때는 보조 스크립트를 사용할 수 있습니다.

1. 검증 화면에서 통과 자료를 확정합니다.
2. `documents.csv 저장` 버튼을 눌러 최종 통과 문서 목록을 내려받습니다.
3. 내려받은 `documents.csv`를 이 폴더의 루트에 둡니다.
4. 아래 명령을 실행합니다.

```bash
python3 scripts/download_documents.py
```

실행 결과:

|결과|설명|
|---|---|
|`downloads/`|원문 파일이 저장되는 폴더|
|`downloaded_documents.csv`|원문 다운로드 결과와 `file_path`가 채워진 문서 목록|

다운로드 폴더 구조 예시:

```text
downloads/
  PHA/
    PHA-0012.pdf
  상신브레이크/
    SANGSIN-0007.html
  SL/
    SL-0045.pdf
```

`downloaded_documents.csv`에는 기존 `documents.csv` 컬럼에 아래 값이 추가 또는 갱신됩니다.

|컬럼|설명|
|---|---|
|`file_path`|내려받은 원문 파일의 상대 경로|
|`download_status`|다운로드완료, 이미존재, 다운로드실패|
|`http_status`|HTTP 응답 코드|
|`content_type`|응답 콘텐츠 유형|
|`download_error`|실패 시 오류 내용|

나중에 청킹할 때는 가능하면 `documents.csv` 대신 `downloaded_documents.csv`를 입력으로 쓰면 됩니다. 이 파일에는 `file_path`가 채워져 있어서 청킹 프로그램이 URL을 다시 열지 않고 로컬 원문 파일을 바로 읽을 수 있습니다.

주의할 점:

- 일부 사이트는 자동 다운로드를 막을 수 있습니다.
- 로그인, 유료 접근, 봇 차단, 세션 필요 자료는 `다운로드실패`로 남을 수 있습니다.
- 실패한 자료는 검증 화면의 `원문 열기` 또는 `원문 다운로드`로 직접 저장한 뒤, `file_path`를 직접 기록하면 됩니다.
- `downloads/`와 `downloaded_documents.csv`는 작업 결과물이므로 기본적으로 Git에 올리지 않습니다.

## 작업자 분배 예시

원본 XLSX의 1행은 헤더이므로 실제 후보는 2행부터 시작합니다.

|작업자|시작 행|검증 행 수|대상|
|---|---:|---:|---|
|작업자 1|2|100|2~101행|
|작업자 2|102|100|102~201행|
|작업자 3|202|100|202~301행|

인원이 늘어나면 시작 행과 검증 행 수만 조정하면 됩니다.

예를 들어 5명이 나누면 `2 / 62 / 122 / 182 / 242`처럼 시작 행을 나누고, 각자 60개 정도씩 검증하면 됩니다.

## 자동 저장과 이어서 하기

검증 상태는 같은 브라우저의 로컬 저장소에 자동 저장됩니다.

다만 다른 사람에게 넘기거나, 다른 PC에서 이어서 하려면 반드시 아래 파일을 내보내야 합니다.

- `상태 JSON 저장`: 현재 진행 상태를 `review_state.json`으로 저장
- `상태 불러오기`: 저장해 둔 `review_state.json`을 다시 불러오기
- `검증 결과 초기화`: 현재 브라우저에 자동 저장된 테스트·검증 상태를 모두 삭제하고 처음부터 다시 시작

권장 방식:

1. 작업을 마칠 때 `상태 JSON 저장`을 누릅니다.
2. 저장된 `review_state.json`을 공유 폴더에 올립니다.
3. 이어서 작업하는 사람은 `상태 불러오기`로 해당 파일을 불러옵니다.

## 체크리스트 기준

통과 자료는 원칙적으로 아래 조건을 모두 만족해야 합니다.

- 본문이 한국어입니다.
- PHA / 상신브레이크 / SL 부품군 중 하나의 대상 부품과 직접 관련됩니다.
- 공정, 소재, 불량원인, 검사, 설비, 안전, 표준 중 하나 이상의 기술 내용이 있습니다.
- 무료로 원문 본문이나 PDF/HTML을 확인할 수 있습니다.
- 제목, 저자 또는 기관, URL, 발행일 또는 연도를 확인할 수 있습니다.
- 동일 문서의 중복본이 아닙니다.

영어 자료는 제외합니다. 원 요청서에는 영어 일부 허용 문구가 남아 있지만, 이후 작업 기준은 한국어 자료만 수집하는 것으로 정리되었습니다.

기업명은 발행 조건이 아닙니다. `PHA`, `상신브레이크`, `SL`은 문서 발행 기업이 아니라 부품군 관리용 분류입니다.

## 요청서 기준 해석

이 도구는 `데이터수집_요청서 (1).md`의 원 요구사항을 바탕으로 만들었지만, 요청서 안의 문장은 검증 기준을 이해하기 위한 참고 자료입니다. 작업자는 README와 검증 화면에 정리된 현재 기준을 우선 적용하면 됩니다.

요청서에서 반영한 핵심 기준은 아래와 같습니다.

|구분|적용 기준|
|---|---|
|수집 분량|최종 목표는 문서 기준 약 300건입니다. 청크 수가 아니라 원문 문서 수 기준입니다.|
|대상 부품군|PHA는 도어 시스템, 상신브레이크는 브레이크 패드·라이닝·마찰재, SL은 램프류·사이드미러·변속레버 중심입니다.|
|기술주제|공정, 소재, 불량원인, 검사·시험, 설비, 안전, 표준 중 하나 이상과 직접 관련되어야 합니다.|
|출처|ScienceON, KIPRIS, 연구기관, 표준기관, 제조사 기술자료, KOSHA, 공공데이터포털 등 공개 출처를 우선합니다.|
|원문 접근|무료로 본문 또는 원문 파일을 확인할 수 있어야 합니다. 유료·로그인 전용·출처 불명 자료는 제외합니다.|
|중복|동일 문서의 다른 판본이나 중복 게재본은 1건으로 계산합니다.|
|최신성|2016년 이후 자료를 우선합니다. 표준, 핵심 특허, 기반 기술은 예외 사유를 기록하고 포함할 수 있습니다.|
|청킹 범위|원문 수집, 텍스트 추출, 청크 분할까지만 수행합니다. 임베딩, 벡터 DB 적재, 요약, 라벨링, 질의응답 생성은 범위 밖입니다.|
|청크 방식|문단·절 경계를 우선하고, 문장 중간에서 끊지 않습니다. 한국어 기준 500~1,000자 권장, 최대 1,500자입니다.|
|표 처리|표는 가능하면 하나의 청크로 유지하고 마크다운 표로 변환합니다. 1,500자를 넘으면 행 단위로 나누되 헤더를 반복합니다.|
|제거 대상|머리말, 꼬리말, 쪽 번호, 목차, 참고문헌 목록, 반복 저작권 문구, 광고성 문구는 제거합니다.|

현재 작업에서 요청서 원문과 다르게 확정한 기준도 있습니다.

|항목|요청서 원문|현재 적용 기준|
|---|---|---|
|언어|한국어 우선, 영어 30% 이내 허용|영어 자료 제외. 한국어 본문만 통과|
|기업명|PHA, 상신브레이크, SL 주력 부품|기업명은 검색·발행 조건이 아니라 부품군 관리용 라벨|
|기업별 내부 분포|출처별 권장 배분 제시|기업별 약 100건 목표만 관리. 내부 부품·주제·출처 비율은 균등할 필요 없음|
|공공데이터포털|외부 데이터셋 포함|원본 데이터 파일이 아니라 데이터셋 설명, 컬럼 정의, 활용 가이드 문서만 청킹 대상|

따라서 검증자는 자료가 특정 기업에서 발행되었는지 보지 말고, 해당 부품군의 기술자료로 실제 활용 가능한지만 판단하면 됩니다.

## 현재 제공되는 파일 구성

압축본 `review-checklist.zip`을 풀면 아래 파일들이 들어 있습니다.

|파일|역할|사용자가 직접 열어야 하는지|
|---|---|---|
|`index.html`|검증 작업 화면|예. 이 파일을 브라우저로 엽니다.|
|`styles.css`|화면 디자인 파일|아니오. 수정하지 않아도 됩니다.|
|`app.js`|검증 저장, 필터, CSV 내보내기 등 기능 파일|아니오. 수정하지 않아도 됩니다.|
|`candidates.js`|HTML에서 바로 읽는 후보 300건 데이터|아니오. 화면이 자동으로 읽습니다.|
|`candidates.json`|후보 300건 원본 데이터의 JSON 버전|필요 시 개발·자동화용으로 사용합니다.|
|`candidates.csv`|후보 300건 원본 데이터의 CSV 버전|엑셀로 후보 목록만 확인하고 싶을 때 사용합니다.|
|`summary.json`|후보 총수와 부품군별 건수 요약|검증용 참고 파일입니다.|
|`README.md`|사용 설명서|예. 작업자에게 같이 전달하면 좋습니다.|
|`scripts/download_documents.py`|`documents.csv` 기준 원문 다운로드 스크립트|최종 통과 문서 원문을 내려받을 때 사용합니다.|

중요한 점은 `index.html`, `styles.css`, `app.js`, `candidates.js`가 같은 폴더에 있어야 한다는 것입니다. `index.html`만 따로 빼서 보내면 화면이 후보 데이터를 읽지 못할 수 있습니다.

## 최종적으로 얻는 파일

검증 작업을 진행하면 사용자는 크게 3종류의 결과 파일을 얻게 됩니다.

### 1. review_state.json

`상태 JSON 저장` 버튼으로 내려받는 파일입니다.

이 파일은 **작업 재개용 저장 파일**입니다. 최종 납품 파일이라기보다, 검증 작업이 중간에 끊겼을 때 이어서 하기 위한 파일입니다.

포함되는 내용:

|항목|설명|
|---|---|
|작업자 이름|화면에서 입력한 검증자 이름|
|시작 행|현재 작업자가 맡은 시작 행|
|검증 행 수|현재 작업자가 맡은 후보 수|
|마지막 후보 위치|마지막으로 보고 있던 후보 ID|
|후보별 검증 상태|미검토, 통과, 보류, 탈락|
|체크리스트 값|한국어, 부품 관련성, 기술주제, 원문 접근, 출처 확인, 중복 여부|
|수정 메타데이터|부품군, 부품, 기술주제, 문서유형, 발행기관, 발행일 등|
|검증 시각|통과, 보류, 탈락 또는 저장을 누른 시각|
|검증 메모|작업자가 남긴 확인 내용|

사용 상황:

- 오늘 하던 검증을 내일 이어서 할 때
- 다른 PC나 다른 사람에게 진행 상태를 넘길 때
- 실수로 브라우저 저장 상태가 날아갈 가능성에 대비할 때

권장 파일명 예시:

```text
review_state_홍길동_2-101.json
review_state_김철수_102-201.json
review_state_이영희_202-301.json
```

포함되는 내용:

|컬럼|설명|
|---|---|
|`candidate_id`|후보 고유 ID|
|`source_row`|원본 XLSX 행 번호|
|`review_status`|미검토, 통과, 보류, 탈락|
|`reviewer`|검증자|

- 전체 작업 현황을 엑셀에서 확인할 때
- 누가 어떤 자료를 검증했는지 추적할 때
- 보류·탈락 자료를 나중에 다시 검토할 때
- 여러 작업자의 결과를 합칠 때

이 파일은 감사 로그에 가깝습니다. 최종 청킹에는 보통 `documents.csv`를 사용하고, `review_results.csv`는 전체 검증 근거로 보관합니다.

### 3. documents.csv

`documents.csv 저장` 버튼으로 내려받는 파일입니다.

이 파일은 **최종 통과 자료만 모은 문서 목록**입니다. 이후 원문 다운로드, 텍스트 추출, 청킹 단계에서 가장 중요하게 쓰는 파일입니다.

`documents.csv`는 `review_status = 통과`인 자료만 포함합니다. 보류, 탈락, 미검토 자료는 들어가지 않습니다.

포함 컬럼:

|컬럼|설명|청킹 단계 사용 여부|
|---|---|---|
|`doc_id`|최종 통과 자료를 `documents.csv`로 저장할 때 자동 생성되는 문서 ID. 청크 ID의 앞부분으로 사용|사용|
|`company`|PHA / 상신브레이크 / SL 등 부품군 관리 라벨|사용|
|`part`|관련 부품명|사용|
|`topic`|공정, 소재, 불량원인, 검사, 설비, 안전, 표준 등|사용|
|`source_type`|논문, 특허, 연구보고서, 표준 등|사용|
|`title`|원문 제목|사용|
|`publisher`|발행기관, 저널, 학회 등|사용|
|`author`|저자|필요 시 사용|
|`published_date`|발행일 또는 발행연도|사용|
|`url`|원문 접근 URL|사용|
|`original_url`|원본 후보 URL|필요 시 사용|
|`access_status`|원문접근가능, 상세페이지확인 등|다운로드 우선순위 판단에 사용|
|`language`|언어. 최종 기준은 `ko`|사용|
|`document_year`|문서 연도|품질 점검에 사용|
|`is_after_2016`|2016년 이후 여부|품질 점검에 사용|
|`year_exception_reason`|2016년 이전 자료를 포함한 이유|품질 점검에 사용|
|`duplicate_key`|중복 확인용 키|중복 제거에 사용|
|`source_domain`|출처 도메인|다운로드 방식 분기 가능|
|`file_path`|나중에 다운로드한 원문 파일 경로|청킹 시 사용|
|`text_extract_status`|텍스트 추출 가능 여부|청킹 준비상태 확인|
|`chunk_count`|청킹 후 생성된 청크 수|청킹 후 업데이트|
|`reviewer`|검증자|이력 관리|
|`reviewed_at`|검증 시각|이력 관리|
|`final_status`|최종 상태. 기본적으로 통과|이력 관리|
|`remarks`|검증 메모|문제 자료 확인|

`documents.csv`는 나중에 아래처럼 이어집니다.

```text
documents.csv
  ↓
원문 다운로드 또는 원문 URL 접근
  ↓
file_path 채우기
  ↓
텍스트 추출
  ↓
청킹
  ↓
chunks_PHA.jsonl / chunks_SANGSIN.jsonl / chunks_SL.jsonl
```

즉, 검증 단계가 끝났을 때 최종적으로 가장 중요한 파일은 `documents.csv`입니다. 이 파일만 있으면 어떤 문서를 청킹해야 하는지, 각 청크에 어떤 메타데이터를 붙여야 하는지 확인할 수 있습니다.

검증 단계에서 작업자가 직접 관리해야 하는 ID는 `candidate_id`와 `source_row`뿐입니다. `doc_id`, `chunk_id`, `chunk_index`는 아직 입력하지 않습니다. `doc_id`는 검수 완료 후 `documents.csv`를 저장할 때 통과 자료를 대상으로 자동 생성합니다. `chunk_id`와 `chunk_index`는 나중에 실제 청킹을 수행할 때 `doc_id`를 기준으로 자동 생성합니다.

### 4. downloaded_documents.csv

`scripts/download_documents.py`를 실행하면 생성되는 파일입니다.

이 파일은 `documents.csv`에 원문 다운로드 결과를 붙인 버전입니다. 청킹 단계에서 가장 쓰기 좋은 입력 파일입니다.

포함되는 추가 정보:

- 원문 파일 경로
- 다운로드 성공 여부
- HTTP 상태 코드
- 콘텐츠 유형
- 실패 사유

청킹 프로그램은 이 파일의 `file_path`를 우선 사용하고, 파일이 없거나 다운로드에 실패한 경우에만 `url`을 다시 확인하면 됩니다.

### 5. 나중에 생성될 청킹 결과 파일

현재 검증 도구가 직접 생성하지는 않지만, 다음 단계에서 최종적으로 만들어야 하는 파일은 아래와 같습니다.

|파일|내용|
|---|---|
|`chunks_PHA.jsonl`|PHA 부품군 통과 문서의 청크|
|`chunks_SANGSIN.jsonl`|상신브레이크 부품군 통과 문서의 청크|
|`chunks_SL.jsonl`|SL 부품군 통과 문서의 청크|
|`README.txt`|수집 기간, 작업자, 분할 도구, 설정값, 특이사항|

청킹 JSONL의 각 줄은 청크 1개입니다. 요청서 기준 필드는 아래와 같습니다.

아래 필드 중 `chunk_id`와 `chunk_index`는 검증 단계의 입력값이 아닙니다. 청킹 프로그램이 문서를 분할하면서 자동으로 붙이는 값입니다.

```text
chunk_id
doc_id
chunk_index
company
part
topic
source_type
title
publisher
published_date
url
section
page
language
text
char_count
```

## 문서유형별 청킹 주의사항

### 특허

문서유형이 `특허`인 경우에는 일반 문서처럼 전체 본문을 순서대로만 자르지 않습니다.

특허문헌은 최소한 아래 구역을 구분해서 청킹해야 합니다.

|특허 구역|`section` 필드 기록 예시|처리 기준|
|---|---|---|
|요약|`요약`|발명의 목적, 핵심 구성, 효과를 담은 요약 부분을 별도 청크로 분리|
|청구항|`청구항` 또는 `청구항 1`, `청구항 2`|권리범위가 되는 청구항을 본문 설명과 섞지 않고 분리|
|발명의 상세한 설명|`발명의 상세한 설명`|기술 구성, 실시예, 작동 방식, 효과 설명을 별도 구역으로 분리|

특허 청킹 예시:

```json
{"chunk_id":"PHA-0012-001","doc_id":"PHA-0012","chunk_index":1,"company":"PHA","part":"도어 래치","topic":"안전","source_type":"특허","title":"도어 열림 방지를 위한 도어 래치 링크구조","publisher":"특허청","published_date":"2017","url":"https://...","section":"요약","page":"","language":"ko","text":"...","char_count":650}
{"chunk_id":"PHA-0012-002","doc_id":"PHA-0012","chunk_index":2,"company":"PHA","part":"도어 래치","topic":"안전","source_type":"특허","title":"도어 열림 방지를 위한 도어 래치 링크구조","publisher":"특허청","published_date":"2017","url":"https://...","section":"청구항 1","page":"","language":"ko","text":"...","char_count":780}
{"chunk_id":"PHA-0012-003","doc_id":"PHA-0012","chunk_index":3,"company":"PHA","part":"도어 래치","topic":"안전","source_type":"특허","title":"도어 열림 방지를 위한 도어 래치 링크구조","publisher":"특허청","published_date":"2017","url":"https://...","section":"발명의 상세한 설명","page":"","language":"ko","text":"...","char_count":980}
```

즉, 특허는 `section` 필드에 반드시 구역명을 넣어야 합니다. 요약, 청구항, 발명의 상세한 설명이 한 청크 안에 섞이면 안 됩니다.

### 공공데이터포털

문서유형이 `데이터셋`이거나 출처가 공공데이터포털인 경우에는 원본 데이터 파일 자체를 청킹 대상으로 삼지 않습니다.

청킹 대상은 아래 문서입니다.

- 데이터셋 설명
- 컬럼 정의
- 데이터 항목 설명
- 활용 가이드
- API 명세 또는 제공 항목 설명
- 갱신 주기, 제공기관, 이용 조건 등 메타데이터 설명

제외 대상:

- CSV, XLSX, JSON 등 원본 데이터 행 전체
- 대량의 반복 레코드
- 단순 코드값 목록만 길게 나열된 원자료

공공데이터포털 자료의 목적은 데이터 자체를 학습시키는 것이 아니라, 해당 데이터셋이 무엇을 의미하고 어떤 항목으로 구성되는지 설명하는 문서를 확보하는 것입니다.

공공데이터포털 청킹 예시:

```json
{"chunk_id":"COMMON-0003-001","doc_id":"COMMON-0003","chunk_index":1,"company":"공통","part":"자동차 부품","topic":"데이터셋","source_type":"데이터셋","title":"자동차 부품 관련 데이터셋 설명","publisher":"공공데이터포털","published_date":"2024","url":"https://www.data.go.kr/...","section":"데이터셋 설명","page":"","language":"ko","text":"...","char_count":720}
{"chunk_id":"COMMON-0003-002","doc_id":"COMMON-0003","chunk_index":2,"company":"공통","part":"자동차 부품","topic":"데이터셋","source_type":"데이터셋","title":"자동차 부품 관련 데이터셋 설명","publisher":"공공데이터포털","published_date":"2024","url":"https://www.data.go.kr/...","section":"컬럼 정의","page":"","language":"ko","text":"...","char_count":840}
```

`documents.csv`에서 그대로 가져오는 필드:

```text
doc_id
company
part
topic
source_type
title
publisher
published_date
url
language
```

청킹 단계에서 새로 만들거나 채우는 필드:

```text
chunk_id
chunk_index
section
page
text
char_count
```

따라서 이 검증 도구는 `chunk_id`를 미리 만드는 도구가 아니라, 나중에 `chunk_id`를 안정적으로 만들 수 있도록 문서 단위의 `doc_id`와 메타데이터를 정리하는 도구입니다.

## 주의사항

- 브라우저 로컬 저장은 같은 PC와 같은 브라우저에서만 유지됩니다.
- 여러 사람이 동시에 작업할 때는 각자 `review_state.json` 또는 `review_results.csv`를 저장한 뒤 합치는 절차가 필요합니다.
- 원문 미리보기가 안 떠도 URL이 죽은 것은 아닐 수 있습니다. 사이트 보안 정책 때문에 iframe 표시가 막히는 경우가 있으니 `원문 열기`로 확인합니다.
- `documents.csv`는 통과 처리된 자료만 저장됩니다. 검증 전에는 비어 있을 수 있습니다.
